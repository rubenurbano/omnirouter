1. ¿Qué es OmniRoute?

OmniRoute es una puerta de enlace (gateway) de IA de código abierto, licencia MIT, que expone un único endpoint local (por defecto http://localhost:20128) compatible con las APIs de OpenAI, Anthropic y Gemini, y que por detrás enruta cada petición hacia uno de sus cientos de proveedores de modelos registrados (OpenAI, Anthropic, Gemini, DeepSeek, Qwen, Kimi, GLM, MiniMax, Groq, y muchos más), con fallback automático, compresión de tokens y enrutamiento inteligente.

Datos concretos publicados en el README para esta versión (DOCUMENTACIÓN OFICIAL, con la advertencia oficial de que se re-auditan cada dos semanas y cambian con el tiempo):

  • 357 proveedores de IA registrados; 154 de ellos con metadatos hasFree: true.
  • El catálogo de modelos de chat cubre 268 proveedores / 2.566 pares proveedor-modelo / 1.312 IDs de modelo en bruto.
  • 455 entradas en el catálogo de free-tier, agrupadas en 40 "pools" recurrentes, de los cuales 20 tienen un presupuesto mensual de tokens publicado y positivo.
  • Cifra de tokens gratuitos: ~1.51 mil millones de tokens/mes de forma estable (hasta ~2.13B el primer mes, sumando créditos de bienvenida de algunos proveedores).
  • 19 estrategias de routing distintas.
  • 110 herramientas en el servidor MCP embebido.
  • Disponible en 43 idiomas de interfaz.
  • 450+ contribuidores.

3. Conceptos fundamentales

Antes de tocar un solo comando, conviene fijar el vocabulario que usa la documentación oficial:

AI Gateway

Un servidor intermedio entre tus aplicaciones/herramientas y los proveedores reales de modelos de IA. Centraliza autenticación, enrutamiento, reintentos y observabilidad.

Provider (proveedor)

Una cuenta/credencial conectada a un backend de IA concreto (por ejemplo, tu cuenta de OpenAI, tu cuenta de Claude Code, una API key de GLM). PROVIDER ≠ MODEL: un mismo provider puede exponer varios models.

Model (modelo)

El modelo de lenguaje/imagen/audio concreto que se invoca dentro de un provider (por ejemplo claude-opus-4-6, gpt-5.5, glm-5.2).

Endpoint unificado

OmniRoute expone /v1/chat/completions (formato OpenAI), /v1/messages (formato Anthropic) y /v1beta/models/... (formato Gemini) desde el mismo servidor, sea cual sea el proveedor real que responde.

OpenAI-compatible API

Cualquier herramienta que sepa hablar con la API de OpenAI (/v1/chat/completions) puede hablar con OmniRoute sin cambios, sólo cambiando la base_url.

Combo

Una cadena de modelos por la que OmniRoute enruta automáticamente, con una estrategia de selección y fallback configurable.

Fallback

Cuando un proveedor falla o se queda sin cuota, OmniRoute reintenta automáticamente con el siguiente proveedor elegible de la cadena.

Routing (enrutamiento)

La lógica que decide, en cada petición, qué proveedor/modelo concreto atiende la llamada.

Free tier

Un nivel de uso gratuito ofrecido directamente por un proveedor (con o sin necesidad de API key), que OmniRoute cataloga y puede usar automáticamente.

Flujo de procesamiento de una petición

Documentado en docs/reference/API_REFERENCE.md (sección "Request Processing"):

  1. El cliente envía la petición a /v1/*.
  2. El route handler llama a handleChat, handleEmbedding, handleAudioTranscription o handleImageGeneration según el endpoint.
  3. Se resuelve el modelo (provider/model directo, alias o combo).
  4. Se seleccionan credenciales desde la base de datos local, filtrando por disponibilidad de cuenta.
  5. En chat: handleChatCore comprueba la caché semántica/de firma y resuelve la configuración de compresión del combo.
  6. Se ejecuta compresión proactiva antes de traducir al formato del proveedor (si está activada: lite, Caveman, RTK o modo apilado/stacked).
  7. El ejecutor del proveedor envía la petición upstream.
  8. La respuesta se traduce de vuelta al formato del cliente (chat) o se devuelve tal cual (embeddings/imágenes/audio).
  9. Se registran el uso, la analítica de compresión y los logs de la petición.
  10. Si hay errores, se aplica el fallback según las reglas del combo.
ℹ️ PERSISTENCIA
OmniRoute usa SQLite (vía better-sqlite3) para toda la persistencia (docs/reference/ENVIRONMENT.md, sección "Storage & Database"). La ruta raíz de datos es DATA_DIR (por defecto ~/.omniroute/), donde vive la base de datos, las copias de seguridad y los ficheros de datos.

5. Requisitos previos

Documentado oficialmente:

  • Node.js: OmniRoute se distribuye como paquete npm (omniroute) y define una versión de Node fijada en .node-version/.nvmrc dentro del repositorio. La documentación no especifica en el README un número de versión mínima públicamente destacado; usa nvm o el gestor de versiones de Node.js que prefieras y confirma con node --version antes de instalar. No documentado oficialmente en las fuentes consultadas: un número de versión mínima concreto fuera del propio repositorio.
  • npm (viene con Node.js) o Docker, según el método de instalación que elijas.
  • Un sistema operativo compatible: Linux, macOS o Windows (OmniRoute se anuncia con Desktop/Electron, PWA y variantes VPS — ver capítulo 29).
  • Conexión a Internet para descargar el paquete y (si se usan) los modelos de proveedores en la nube.
  • Opcional pero recomendado: al menos una cuenta o API key de algún proveedor si quieres ir más allá de los proveedores gratuitos sin clave que trae preconfigurados (auto funciona sin ninguna clave desde el primer arranque).

6.5 Detener y reiniciar

  • Para detener el servidor lanzado con omniroute directamente: Ctrl+C en la terminal donde corre.
  • Para reiniciar de forma controlada (sin matar el proceso desde fuera) existe el endpoint de gestión:
bash
curl -X POST http://localhost:20128/api/restart
curl -X POST http://localhost:20128/api/shutdown

Ambos endpoints están documentados en docs/reference/API_REFERENCE.md, bajo "Internal / System APIs", como "used internally by the system... not typically called by end users", así que trátalos como utilidades de administración avanzada, no como el flujo normal de parar/arrancar.

6.6 Actualizar OmniRoute

Documentado en docs/guides/CLI-INTEGRATIONS.md:

bash
omniroute update --check      # comprueba si hay una versión más nueva (exit code 1 si la hay)
omniroute update --dry-run    # muestra exactamente el comando que se ejecutaría, sin aplicarlo
omniroute update --apply      # instala sin preguntar
omniroute update              # modo interactivo (pide confirmación)
omniroute update --changelog  # muestra el changelog
omniroute update --no-backup  # omite la copia de seguridad previa a actualizar
omniroute update --yes        # confirma automáticamente

El comando real que ejecuta por debajo, siempre, es:

bash
npm install -g omniroute@latest --include=optional
⚠️ FLAG IMPORTANTE
El flag --include=optional es importante: garantiza que las dependencias opcionales nativas (better-sqlite3, keytar, tls-client, la pila de LLMLingua) sobreviven a la actualización aunque tu configuración de npm tenga omit=optional.

bash

# borra el directorio DATA_DIR (por defecto ~/.omniroute/):
rm -rf ~/.omniroute

6.8 Problemas habituales en la instalación

Ver el capítulo 32 (Troubleshooting) para el detalle. Los más comunes documentados indirectamente por las variables de entorno del proyecto:

  • El puerto 20128 ya está en uso: cambia PORT (ver capítulo 31).
  • La build nativa de SQLite falla en npm install: existe OMNIROUTE_SKIP_POSTINSTALL=1 para saltar el warm-up nativo en instalaciones headless/CI, útil si SQLite ya viene compilado.
  • Faltan dependencias opcionales tras actualizar con un gestor de paquetes que omite optionalDependencies: usa siempre omniroute update (o npm install -g omniroute@latest --include=optional), nunca un npm update genérico si tu .npmrc tiene omit=optional.

8. El Dashboard

El dashboard es la interfaz web de administración, servida en el mismo puerto que la API (modo de puerto único por defecto) o en un puerto separado (modo split ports, ver capítulo 31).

Secciones documentadas oficialmente en docs/reference/API_REFERENCE.md y en el README (rutas reales del dashboard citadas en la documentación):

  • /dashboard/free-tiers — catálogo y consumo en vivo de los free tiers.
  • /dashboard/analytics/* — analítica de auto-routing, compresión y diversidad de proveedores.
  • /dashboard/compression/exclusions — exclusión de modelos/endpoints de la compresión.
  • /dashboard/acp-agents — agentes ACP detectados.
  • /dashboard/settings/modality-bridge — configuración de los puentes de visión/audio/vídeo (pestañas Vision, Audio, Video).

El dashboard permite, entre otras cosas (según las rutas de API que respalda cada pantalla): añadir/editar/probar proveedores, gestionar API keys, crear combos de routing, configurar compresión, revisar logs y analítica de uso, gestionar backups, configurar webhooks, y administrar el servidor MCP y A2A.

9. Providers (proveedores)

9.1 Provider ≠ Model

Un provider es la cuenta/credencial conectada (por ejemplo, tu OAuth de Claude Code, o una API key de GLM). Un model es el modelo concreto que ese provider expone. Un mismo provider puede servir varios modelos; un mismo modelo lógico (p. ej. claude-opus-4-6) puede estar accesible a través de varios providers distintos con distinto coste, cuota y latencia.

9.2 Tipos de proveedores documentados

Según el README y docs/reference/PROVIDER_REFERENCE.md (referenciado desde el README):

Proveedores con API key

La mayoría — OpenAI, Anthropic, Gemini, DeepSeek, Mistral, Qwen, Meta Llama (vía distintos hosts), Groq, NVIDIA, MiniMax, Cohere, Perplexity, HuggingFace, Together, Fireworks, Cloudflare, Baidu, y muchos más.

Proveedores OAuth

Por ejemplo Claude Code, Codex/ChatGPT, Ollama Cloud, Kimi Code, Grok Build (xAI) — la documentación menciona explícitamente flujos OAuth para varios de estos ("Grok Build (xAI) with browser + OAuth login").

9.3 Cómo añadirlos, probarlos, editarlos y eliminarlos (CLI)

12.12 Ejemplo: aplicación profesional (con reintento manual y logging)

python
import logging
import time
from openai import OpenAI

logging.basicConfig(level=logging.INFO)
client = OpenAI(base_url="http://localhost:20128/v1", api_key="your-api-key")

def ask(prompt: str, retries: int = 3):
    for attempt in range(1, retries + 1):
        try:
            resp = client.chat.completions.create(
                model="auto",
                messages=[{"role": "user", "content": prompt}],
                timeout=30,
            )
            return resp.choices[0].message.content
        except Exception as exc:
            logging.warning("Intento %s falló: %s", attempt, exc)
            time.sleep(2 ** attempt)
    raise RuntimeError("Todos los reintentos fallaron")
ℹ️ NOTA IMPORTANTE

16.1 Qué es y por qué usarlo

El routing decide, para cada combo, a qué target enviar cada petición cuando hay varios elegibles. Es el corazón de la resiliencia y del ahorro de coste de OmniRoute.

16.2 Zero-config: usar auto

16.4 Cuándo usar cada una (guía práctica)

  • priority: cuando tienes un orden claro de preferencia (p. ej. tu suscripción de pago primero, luego una API key, luego un free tier). No la uses si quieres repartir carga uniformemente.
  • cost-optimized: cuando el coste es tu prioridad número uno y te da igual qué proveedor concreto responde. No la uses si necesitas coherencia de proveedor entre turnos de una misma conversación (mejor cache-optimized o lkgp en ese caso).
  • round-robin / weighted: cuando quieres repartir tráfico entre varias cuentas del mismo proveedor para no agotar la cuota de una sola. No la uses si un objetivo es mucho más lento o caro que los demás sin un peso que lo compense.
  • fusion: cuando la calidad de la respuesta importa más que la latencia o el coste, y quieres comparar/combinar varias opiniones de modelos distintos. No la uses para tareas de baja latencia o alto volumen (multiplica el coste por el número de modelos del panel).
  • lkgp: cuando quieres estabilidad de proveedor a lo largo de una sesión, con fallback discreto si ese proveedor deja de estar sano.

17.3 Las 3 capas de resiliencia independientes

Documentadas oficialmente en el README ("Resilience is built in — 3 independent layers"):

Capa 1 — Circuit breaker de proveedor (afecta a todo el proveedor)

  • Salta sólo con errores 408/5xx.
  • Umbrales: OAuth 10×, API-key 15×, local 2×.
  • Se reinicia a los 60s/30s/15s respectivamente, entrando en una prueba HALF-OPEN (recuperación perezosa).
  • Mientras el breaker está OPEN, el combo redirige al siguiente proveedor.

Capa 2 — Cooldown de conexión (afecta a una sola clave/cuenta)

  • Base de 5s (OAuth) / 3s (API key), con backoff exponencial ×2 y protección contra thundering herd.
  • Un 429 respeta la cabecera Retry-After.
  • Un éxito limpia todo el estado de error.
  • Mientras una clave está en cooldown, las claves hermanas siguen sirviendo.

Capa 3 — Bloqueo (lockout) de modelo (afecta a un solo modelo)

  • Un 429 propio del modelo, un 404 local, o denegaciones de modo bloquean sólo ese modelo, nunca toda la conexión.
  • Los estados terminales (cuenta baneada, expirada, créditos agotados) son para que el operador actúe manualmente — no entran en cooldown automático.

Compresión de tokens (RTK, Caveman, LLMLingua-2 y más)

Cap. 20 — Modos, motores, pipelines, analítica y exclusiones

20.1 Qué problema resuelve

Los tokens son la unidad con la que los proveedores de IA miden y cobran el texto que envías y recibes. Las salidas de herramientas (tests, logs de build, salidas de terminal) suelen ser muy verbosas y queman tokens sin aportar información nueva al modelo. OmniRoute comprime ese contenido antes de enviarlo al proveedor, ahorrando coste y espacio de contexto.

20.2 Modos de compresión (tabla oficial)

ModoMotor(es)Entrada pensada
offningunoPreservación exacta del prompt
liteayudantes ligeros de CavemanLimpieza siempre-activa de bajo riesgo
standardCavemanCondensación de prompts en lenguaje natural
aggressiveCaveman + resumidores de historial/herramientasSesiones de chat largas
ultraCaveman + podaRecuperación de límite de contexto
rtkRTKSalida de terminal, shell, build, tests y git

20.3 Caveman

Se centra en la condensación semántica de prosa normal:

  • preserva bloques de código, URLs, JSON, rutas y datos estructurados
  • elimina relleno, atenuaciones, contexto repetido y conectores verbosos
  • soporta paquetes de reglas por idioma en open-sse/services/compression/rules/

Cifras publicadas por el propio Caveman aguas arriba (documentadas, no garantías universales): ~75% menos tokens de salida, 65% de ahorro medio de salida en benchmarks (rango 22–87%), y una herramienta de ~46% de compresión de entrada. OmniRoute usa la cifra de entrada de Caveman al documentar el ahorro combinado (stacked).

20.4 RTK

Se centra en la salida de comandos y herramientas:

  • detecta clases de salida como git status, git branch, git diff, Vitest/Jest/Pytest, Cargo/Go tests, builds de TypeScript/Vite/Webpack, ESLint, npm audit/install, logs de Docker, find/grep de shell, trazas de pila y logs genéricos
  • aplica 49 filtros JSON
  • soporta un pipeline declarativo estilo RTK: eliminación de ANSI, reemplazo, cortocircuito por coincidencia de salida, recorte de líneas por cabeza/cola/longitud máxima, y salida de reserva cuando el resultado queda vacío

Cifra publicada por RTK aguas arriba: 60–90% de ahorro en compresión de salida de comandos. Su ejemplo de README muestra una sesión de 30 minutos de Claude Code pasando de ~118.000 tokens a ~23.900, es decir, 79.7% ahorrado.

20.5 LLMLingua-2 (poda semántica)

Motor de poda semántica de tokens sobre prosa, usando un clasificador ONNX pequeño (TinyBERT por defecto, ~57 MB; hay un modelo BERT-base opcional de mayor precisión, ~710 MB). Es opcional (optionalDependencies de npm) y falla en abierto: si faltan las dependencias o hay cualquier error, devuelve el texto original sin tocar, nunca lanza un error. Para activarlo en un entorno reducido:

bash
npm install @atjsh/llmlingua-2@2.0.5 js-tiktoken

20.6 Pipelines apilados (stacked)

El modo stacked por defecto ejecuta: rtk -> caveman

Cuando ambos motores reducen la misma parte del contenido, el ahorro se combina multiplicativamente:

fórmula
combinado = 1 - (1 - ahorro_RTK) * (1 - ahorro_entrada_Caveman)
media     = 1 - (1 - 0.80) * (1 - 0.46) = 89.2%
rango     = 1 - (1 - 0.60..0.90) * (1 - 0.46) = 78.4%–94.6%

Es de aquí de donde sale la cifra que verás repetida en el README: "RTK + Caveman ahorra 15–95% de tokens (~89% de media)".

Guardrails

Cap. 24 — Comprobaciones de seguridad, política y transformación de contenido

24.1 Qué son y cómo se ejecutan

Los guardrails aplican comprobaciones de seguridad, política y transformaciones de contenido en la frontera entre OmniRoute y los proveedores. Cada uno puede inspeccionar (y opcionalmente rechazar, transformar o anotar) el payload de la petición (preCall) y la respuesta del proveedor (postCall).

ℹ️ SISTEMA FAIL-OPEN
Si un guardrail lanza una excepción durante su ejecución, el registro anota el error y continúa con el siguiente guardrail en lugar de fallar la petición completa. Bloquear es siempre una decisión explícita (block: true), nunca un accidente.

24.2 Los 6 guardrails integrados (orden de prioridad)

PrioridadNombreEtapa(s)
5vision-bridgepreCall
6audio-bridgepreCall
7video-bridgepreCall
10pii-maskerpre + post
20prompt-injectionpreCall
95credential-maskerpre + post

Los números de prioridad más bajos se ejecutan primero.

24.3 Vision / Audio / Video Bridge

Interceptan peticiones con contenido multimedia dirigidas a modelos que no soportan esa modalidad, y transparentemente:

  • reenrutan toda la petición a un modelo con esa capacidad, o
  • describen el contenido (imagen/audio/vídeo) con texto generado por un modelo auxiliar configurable, sustituyendo las partes multimedia por su descripción textual, antes de la llamada upstream.

Esto permite que proveedores sólo-texto manejen de forma transparente peticiones multimodales. Cabecera de transparencia en la respuesta cuando se aplica: x-omniroute-modality-bridge: image->text;model=<visionModel>;parts=<n> (equivalente para audio y vídeo).

24.4 PII Masker

Se ejecuta en ambas etapas:

  • preCall: recorre system, messages, input y prompt, y aplica detección de PII. Si PII_REDACTION_ENABLED=true, redacta la PII detectada en el payload saliente. Si está desactivado, sólo registra el conteo de detecciones sin reescribir.
  • postCall: recorre la respuesta y aplica sanitización de PII también sobre el formato de la Responses API.

El guardrail nunca bloquea: sólo anota o reescribe.

24.6 Credential Masker

Redacta patrones de claves API/secretos conocidos (OpenAI, Anthropic, Google, GitHub, Slack, AWS, Stripe, JWTs, cadenas de conexión con credenciales, cabeceras Authorization/x-api-key...) tanto en la petición saliente como en la respuesta. Opt-in: desactivado salvo que CREDENTIAL_REDACTION_ENABLED=true.

24.5 Prompt Injection

Detecta estructuras adversariales en el contenido suministrado por el usuario.

AjusteVariable de entornoPor defectoEfecto
ActivadoINPUT_SANITIZER_ENABLEDtruefalse desactiva el guardrail
ModoINJECTION_GUARD_MODE / INPUT_SANITIZER_MODEwarnblock, warn o log
Umbral de bloqueoINPUT_SANITIZER_BLOCK_THRESHOLDhighSeveridad mínima que bloquea en modo block
⛔ LIMITACIÓN OFICIAL
Estas guardas son detecciones heurísticas de mejor esfuerzo, no un firewall completo de inyección de prompts ni un sistema DLP de PII completo. Pueden producir falsos positivos (prompts de rol/RPG legítimos marcados) y falsos negativos (leetspeak, espaciado, patrones no ingleses). No son suficientes por sí solas para cumplimiento normativo — pruébalas contra tu propio tráfico antes de depender de ellas.

El escaneo tiene un límite de 16 KB sobre el texto del prompt (MAX_INJECTION_SCAN_BYTES), para acotar el coste de CPU/GC en payloads muy grandes.

24.7 Desactivar guardrails por petición

header

También se puede fijar por API key (apiKeyInfo.disabledGuardrails) o en el propio cuerpo de la petición (disabledGuardrails o metadata.disabledGuardrails).

24.8 Guardrails personalizados

Seguridad

Cap. 25 — Prohibiciones, producción, secretos, cifrado, SSRF

25.1 Nunca hagas esto

⛔ LISTA DE PROHIBICIONES
  • No dejes INITIAL_PASSWORD en su valor por defecto (CHANGEME).
  • No expongas el dashboard directamente a Internet sin autenticación reforzada.
  • No compartas JWT_SECRET, API_KEY_SECRET ni OMNIROUTE_WS_BRIDGE_SECRET entre entornos, ni los subas al control de versiones (.env ya está en .gitignore, pero verifícalo tú mismo antes de hacer push).
  • No actives CORS_ALLOW_ALL=true en producción — es explícitamente "development-only" según la documentación.
  • No actives AUTH_COOKIE_SECURE=false si sirves detrás de HTTPS.
  • No dejes ALLOW_API_KEY_REVEAL=true en una instancia compartida por varias personas.
  • No publiques OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS=true en un despliegue público sin entenderlo — está pensado para permitir proveedores locales de confianza (Ollama, LM Studio...), no para exponerlos a Internet.

25.2 Configuración recomendada de producción (documentada oficialmente)

25.5 Protección contra SSRF y exposición local

  • OUTBOUND_SSRF_GUARD_ENABLED=true (por defecto): bloquea llamadas de proveedor hacia rangos IP privados/loopback/link-local.
  • OMNIROUTE_ALLOW_PRIVATE_PROVIDER_URLS=false (por defecto): hay que activarlo explícitamente para usar proveedores auto-alojados (LM Studio, Ollama, vLLM, Llamafile, Triton, SearXNG).
  • Los endpoints de metadatos de nube (169.254.169.254, metadata.google.internal) permanecen siempre bloqueados, sin excepción.

25.6 Sanitización de entrada y PII

Ver capítulo de Guardrails para el detalle de INPUT_SANITIZER_*, PII_REDACTION_ENABLED, PII_RESPONSE_SANITIZATION y CREDENTIAL_REDACTION_ENABLED.

25.7 Exposición pública / VPS

Cuando expongas OmniRoute más allá de localhost:

  • Ponlo detrás de un proxy inverso con TLS (nginx, Caddy) y fija NEXT_PUBLIC_BASE_URL a tu dominio público estable.
  • Considera el gate OIDC opcional del dashboard (OMNIROUTE_OIDC_DISABLE_PASSWORD_LOGIN), manteniendo siempre disponible el login por contraseña salvo que decidas explícitamente forzar SSO.
  • Revisa docs/security/MITM-TPROXY-DECRYPT.md si necesitas capturar CLIs que ignoren las variables de proxy del entorno — es una capacidad avanzada y explícita del proyecto, no algo a activar por defecto.

25.8 Riesgos y consideraciones honestas

  • Las guardas de inyección de prompt y PII son heurísticas de mejor esfuerzo (ver 24.5); no sustituyen una auditoría de seguridad de cumplimiento normativo.
  • OmniRoute es local-first: por defecto tus claves y tu tráfico no salen de tu máquina/VPS salvo hacia el proveedor que elijas — pero tú sigues siendo responsable de la seguridad del host donde lo despliegues.

Troubleshooting y Diagnóstico

Cap. 32 — Troubleshooting por síntomaCap. 33 — Diagnóstico (omniroute doctor)

Organizado por síntoma, tal como pide un manual profesional. Las soluciones se apoyan directamente en el comportamiento documentado oficialmente; donde la causa exacta no está confirmada en las fuentes consultadas, se indica.

Posibles causas:

  • El servidor no ha arrancado (revisa la terminal donde ejecutaste omniroute).
  • Estás usando un puerto distinto al que crees — revisa PORT, API_PORT, DASHBOARD_PORT.
  • OMNIROUTE_BASE_PATH está fijado y estás accediendo a la raíz en vez de a la subruta.

Solución: confirma el puerto con curl http://localhost:20128/api/monitoring/health; si usas puertos separados, el dashboard vive en DASHBOARD_PORT, no en API_PORT.

Diagnóstico:

  • Comprueba el estado del proveedor: GET /api/monitoring/health o la pantalla de Providers en el dashboard.
  • Revisa si está en cooldown de conexión (Capa 2 de resiliencia): GET /api/rate-limits.
  • Revisa si el circuit breaker de ese proveedor está OPEN (Capa 1): usa POST /api/resilience/reset para forzar un reseteo si estás seguro de que el proveedor ya está sano.
  • Si usas un proxy de salida, revisa HTTP_PROXY/HTTPS_PROXY/SOCKS_HANDSHAKE_TIMEOUT_MS.
  • Comprueba que el proveedor que lo sirve está conectado y con credenciales válidas (GET /api/providers/[id]/models).
  • Revisa el modo de prefijo (?prefix=alias|dual|canonical en /v1/models) — puede que el modelo exista pero bajo un id distinto al que esperabas.
  • Si es un modelo personalizado, confirma que no está oculto (GET/PATCH /api/provider-models).

Clave ausente o inválida. Si REQUIRE_API_KEY=true, toda petición a /v1/* necesita Authorization: Bearer <clave-válida>.

El id de modelo no existe en el catálogo actual, o el endpoint no existe (revisa la tabla de endpoints de compatibilidad del capítulo API para confirmar la ruta exacta).

Límite de tasa alcanzado. Puede venir de:

  • Un límite de tasa por API key (DEFAULT_RATE_LIMIT_PER_DAY o límites explícitos vía /api/usage/token-limits).
  • Un cooldown de conexión activo en el proveedor elegido (respeta la cabecera Retry-After).
  • Contención de una exclusive managed session lease, con cuerpo {"state":"WAITING_FOR_CAPACITY", ...}.
  • Confirma que estás llamando a un combo o a auto, no a un provider/model fijo y único — el fallback sólo actúa dentro de un combo con varios objetivos.
  • Revisa X-OmniRoute-Fallback-Attempts en la respuesta: si nunca aparece, es que nunca hizo falta reintentar (todo fue bien a la primera) — no confundas "no hizo falta" con "no funciona".
  • Comprueba que hay más de un objetivo elegible y sano en el combo (GET /api/combos/metrics).

Ver capítulo Docker, problemas habituales — falta el volumen en DATA_DIR, o DATA_DIR no apunta a la ruta montada.

  • ¿Faltan los secretos obligatorios (JWT_SECRET, API_KEY_SECRET, INITIAL_PASSWORD, y en producción OMNIROUTE_WS_BRIDGE_SECRET)? Sin ellos, la app puede negarse a arrancar o (peor) operar con valores por defecto inseguros.
  • ¿El puerto ya está en uso? Cambia PORT.
  • ¿Falló el healthcheck de la base de datos SQLite en el arranque? Prueba OMNIROUTE_SKIP_DB_HEALTHCHECK=1 temporalmente para aislar el problema (no lo dejes así en producción).
  • Ejecuta omniroute doctor (capítulo 33).
  • ¿El modelo/endpoint está en la lista de exclusiones de compresión (Dashboard → Compression → Exclusions)?
  • Con LLMLingua-2 seleccionado: si las dependencias opcionales no están instaladas, el motor falla en abierto silenciosamente (devuelve el texto sin tocar, sin error) — instala @atjsh/llmlingua-2@2.0.5 y js-tiktoken (cap. 20.5).
  • Con perfiles coding-safe/balanced de OmniGlyph: si la sesión aún no ha acumulado historial, el motor puede no transformar nada (below_min_chars) — es un comportamiento documentado, no un fallo.

36. Buenas prácticas profesionales

  • Separa desarrollo y producción: usa DATA_DIR distintos (o instancias distintas) para no mezclar claves/cuotas de prueba con las reales.
  • Gestión de claves: usa siempre --credential-env/--credential-stdin en la CLI en vez de pasar claves en texto plano; no dejes ALLOW_API_KEY_REVEAL=true en instancias compartidas.
  • Observabilidad: revisa X-OmniRoute-Decision y las cabeceras de coste en cada integración crítica; usa /api/analytics/* (auto-routing, compresión, diversidad) periódicamente.
  • Logs: activa/gestiona NO_LOG_API_KEY_IDS si necesitas excluir ciertas claves del registro por cumplimiento normativo (GDPR).
  • Fallback: diseña tus combos con al menos dos niveles (por ejemplo, tu suscripción + un proveedor de pago por token) — no dependas de un único proveedor para nada crítico.
  • Redundancia y diversidad: vigila /api/analytics/diversity; si un proveedor concentra la mayoría del tráfico, es un punto único de fallo.
  • Costes: usa auto/cheap o cost-optimized para tareas donde la calidad exacta del modelo no importa; usa presupuestos por clave (/api/usage/budget) para poner un techo de gasto.
  • Límites: fija token-limits por modelo/proveedor/global si compartes la instancia con varios equipos.
  • Seguridad: repasa el capítulo de Seguridad completo antes de exponer cualquier instancia fuera de localhost.
  • Backups: automatiza POST /api/db-backups (backup manual) o confía en el automático (no desactives DISABLE_SQLITE_AUTO_BACKUP sin sustituirlo por tu propia estrategia).
  • Actualizaciones: usa siempre omniroute update (nunca un npm update genérico), para no perder las dependencias nativas opcionales.
  • Pruebas: antes de depender de una guarda de seguridad (inyección de prompt, PII) en producción, pruébala contra tráfico real — la propia documentación advierte de que son heurísticas de mejor esfuerzo.
  • Monitorización: integra /api/telemetry/summary y /api/monitoring/health en tu sistema de monitorización externo (Prometheus, Grafana, etc. — la exposición del dato es tuya, OmniRoute no publica un exportador Prometheus documentado en las fuentes consultadas).

41.5 Reintentos y cola de mensajes muertos

Documentado: 3 intentos con backoff exponencial y, si los tres fallan, el evento pasa a una cola de mensajes muertos (dead-letter queue) en vez de perderse silenciosamente. AGENTS.md (documentación interna del propio repositorio) confirma además que tras 10 fallos consecutivos un webhook se auto-desactiva.

41.4 Verificación de firma

Cada payload incluye la cabecera X-OmniRoute-Signature (HMAC-SHA256), calculada con el secreto que definiste al crear el webhook. Verifica siempre esta firma en tu receptor antes de confiar en el contenido del payload — es el mecanismo documentado para confirmar que la petición viene realmente de tu instancia de OmniRoute y no de un tercero que adivinó tu URL.

✅ EJEMPLO
Ejemplo de verificación en Python (patrón estándar de HMAC-SHA256, no un fragmento de código copiado literalmente de la documentación, que no publica el snippet exacto en las fuentes consultadas):
python
import hmac, hashlib

def verificar_firma(payload_bytes: bytes, firma_recibida: str, secreto: str) -> bool:
    esperada = hmac.new(secreto.encode(), payload_bytes, hashlib.sha256).hexdigest()
    return hmac.compare_digest(esperada, firma_recibida)

41.6 Caso práctico: alerta cuando un proveedor cae

  1. Crea un webhook apuntando a tu propio endpoint (por ejemplo, un canal de Slack vía un pequeño relay HTTP).
  2. Suscríbete al evento provider.unavailable.
  3. En tu receptor, verifica X-OmniRoute-Signature y publica una alerta con el nombre del proveedor afectado.
  4. Complementa con circuit_breaker.opened/circuit_breaker.closed para saber exactamente cuándo un proveedor entra y sale de fallo, sin tener que hacer polling manual de /api/monitoring/health.

47.7 Encadenar instancias de OmniRoute entre sí (peer chaining)

Otra instancia de OmniRoute se puede añadir como proveedor "Custom OpenAI-compatible", usando la /v1 del peer y una clave dedicada de mínimo privilegio emitida por ese peer. Para cadenas recíprocas o de varios saltos, activa la guarda de bucle opt-in en cada gateway:

env
# gateway-a
OMNIROUTE_INSTANCE_ID=gateway-a
OMNIROUTE_PEER_URLS=http://gateway-b:20128/v1
OMNIROUTE_PEER_MAX_HOPS=4

# gateway-b
OMNIROUTE_INSTANCE_ID=gateway-b
OMNIROUTE_PEER_URLS=http://gateway-a:20128/v1
OMNIROUTE_PEER_MAX_HOPS=4

Un ID de instancia repetido o un presupuesto de saltos agotado devuelve HTTP 508 Loop Detected.

⛔ IMPORTANTE
Encadenar peers no es replicación de base de datos ni failover de host — cada gateway mantiene su propio estado SQLite, cachés, contadores de tasa y sesiones independientes. Nunca montes una misma base de datos SQLite en varias instancias de OmniRoute corriendo a la vez.

47.8 Estrategias de balanceo a nivel de cuenta vs. a nivel de combo

ℹ️ ACLARACIÓN DOCUMENTADA IMPORTANTE
El dashboard (Settings → Routing) expone explícitamente 6 estrategias de routing a nivel de cuenta (las más usadas): Fill First, Round Robin, P2C, Random, Least Used, Cost Optimized. Estas son un subconjunto simplificado de las 19 estrategias completas aplicables a nivel de combo (capítulo Routing), que sí incluyen lkgp, context-optimized, context-relay, fusion, pipeline, etc. Si buscas una estrategia avanzada y no la ves en Settings → Routing, es porque esa pantalla sólo expone el subconjunto de cuenta — configúrala directamente en el combo.

API: interfaz de programación de aplicaciones; el conjunto de endpoints HTTP que expone OmniRoute.

Caveman: motor de compresión centrado en condensar prosa en lenguaje natural.
Combo: cadena de modelos por la que OmniRoute enruta automáticamente, con estrategia y fallback configurables.
Compresión (Compression): reducción del número de tokens enviados/recibidos, preservando la información relevante.
Endpoint: una ruta HTTP concreta de la API (por ejemplo /v1/chat/completions).
Fallback: mecanismo de reintento automático hacia el siguiente objetivo elegible cuando uno falla.
Free tier: nivel de uso gratuito ofrecido directamente por un proveedor externo.
Guardrail: comprobación/transformación de seguridad o política aplicada antes (preCall) o después (postCall) de la llamada al proveedor.
JWT: JSON Web Token; formato de token usado para las cookies de sesión del dashboard.
MCP (Model Context Protocol): protocolo estándar para que un cliente de IA consuma "herramientas" expuestas por un servidor.
Model: el modelo de IA concreto invocado (por ejemplo gpt-5.5).
OAuth: flujo de autorización delegada usado por algunos proveedores (Claude Code, Codex/ChatGPT, etc.) en vez de una API key estática.
PII: información de identificación personal.
Provider: la cuenta/credencial conectada a un backend de IA concreto.
Router / Routing: la lógica que decide, en cada petición, a qué proveedor/modelo enviarla.
RTK: motor de compresión centrado en la salida de comandos y herramientas (terminal, tests, builds, git).
Skill (A2A/Skills framework): una capacidad concreta expuesta por un agente o por el framework de Skills de OmniRoute.
Streaming: entrega de la respuesta en fragmentos progresivos (Server-Sent Events / WebSocket) en vez de esperar la respuesta completa.
VPS: servidor privado virtual, típico destino de un despliegue de producción de OmniRoute.

39. Limitaciones y honestidad técnica

Este tutorial no maquilla ni omite lo que la propia documentación oficial reconoce como limitación:

  • Las guardas de inyección de prompt y PII son heurísticas de mejor esfuerzo, no un firewall completo ni un sistema DLP de cumplimiento normativo — pueden fallar en ambas direcciones (falsos positivos y falsos negativos).
  • Los free tiers no son una garantía permanente: las cifras de tokens gratuitos se re-auditan cada dos semanas y pueden subir o bajar según lo que hagan los proveedores externos, fuera del control de OmniRoute. El propio proyecto marca explícitamente 15 proveedores como "a evitar" en su catálogo de riesgo de términos de servicio.
  • La compresión no es gratis en todos los sentidos: es una transformación con pérdida en varios de sus modos (aggressive, ultra); para casos donde el byte-a-byte del prompt importa (evals deterministas, prefijos sensibles a caché), existe un mecanismo explícito de exclusión — úsalo.
  • LLMLingua-2 depende de dependencias opcionales que, si faltan, hacen que el motor falle en abierto de forma silenciosa (sin avisar) — comprueba activamente que está funcionando si lo activas.
  • Dependencia de proveedores externos: OmniRoute no controla la disponibilidad, el precio ni los términos de servicio de los proveedores reales; sólo orquesta el acceso a ellos.
  • Zonas no cubiertas por la documentación oficial consultada: Termux/Android, un ejemplo íntegro de docker-compose.yml/unidad systemd, y una guía "Windows paso a paso" dedicada no aparecen desarrolladas en las fuentes Markdown revisadas para este tutorial — se ha señalado explícitamente cada vez que esto ocurre, en lugar de rellenar el hueco con una suposición.
